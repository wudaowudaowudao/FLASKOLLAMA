# 引言  

为深入推动中国中车进一步深化科技体制改革，推进科技创新与产业创新的深度融合，按照大创新体系进一步优化协同创新生态，提升创新效率与产品竞争力，构建轨道交通装备和清洁能源装备“双赛道双集群”适用的研发数字化体系，推动产品研发实现双赛道产业兼容、多维度体系融合、分层式研发递进、全生命周期贯通、穿透式精准管理、数智化高效赋能。  

依据大创新体系建设总体思路、中车产品研发管理总体要求和研发数智化转型的“1个研发生态、1套体系标准、N个案例应用、4个企业能力建设”的总体目标，形成一套研发数字化体系标准规范。通过构建指南系统性指导研发数字化建设工作，通过流程规范统筹全集团研发流程，通过数据架构设计规范和应用架构设计规范统筹数据架构和信息系统架构建设，通过研发指标与成熟度评价推进研发数字化体系的建设与持续改进。  

Q/CRRC丁278《研发数字化体系》拟由6部分组成：  

-—第1部分：构建指南。目的在于描述研发数字化体系的总体框架，给出业务架构、数据架构、应用架构的设计要点，提出体系运行评价和体系支撑保障建设要点。  
一—第2部分：流程规范。目的在于规定研发数字化体系中研发流程的定义和划分原则，明确研发流程的管理内容和管控要求、输入和输出要求。-—第3部分：数据架构设计规范。目的在于规定研发数字化体系中数据架构的组成及管理原则，明确研究数据资源目录、数据标准、数据模型和数据分布的设计方法。  
—第4部分：应用架构设计规范。目的在于规定研发数字化体系中应用架构的组成及管理原则，明确应用架构设计方法。  
一—第5部分：研发指标。目的在于规定研发域指标框架，明确研发投入、研发过程、研发效果等维度的指标定义规则。  
一—第6部分：成熟度评价规范。目的在于规定研发数字化体系成熟度评价模型，明确成熟度等级和关键过程评价要素。

# 5.2数据架构设计原则  

研发数据架构设计应遵循以下原则：  

a）全局覆盖：研发数据架构的设计立足于企业研发全局视角，覆盖所有研发业务，确保研发数据的完整性和一致性;  
b）业务导向：研发数据架构的设计应基于研发业务架构，匹配研发业务流程，并符合研发管理规则及需求;  
c）统一目录管理：企业应遵循统一的数据层级架构，建设完整的研发数据资源目录;  
d）前瞻规划：企业应以满足未来研发业务管理、系统建设、数据分析等应用需求为基础，科学定义研发业务对象的属性标准，提升数据架构的可扩展性和灵活性;  
e）认证数据源：各项研发数据应严格认证数据源，确保数据的准确性和可追溯性。  

# 6研发数据架构设计  

# 6.1搭建研发数据资源目录  

# 6.1.1 确定研发主题域分组和研发主题域  

企业应根据研发业务流程架构的流程分类和流程组，按照一致原则分别确定研发数据的主题域分组和主题域，并保持数据责任人与业务流程责任人一致。按照Q/CRRC」278.2的L1流程分类“研发管理”，定义研发主题域分组（DL1）为“研发管理”，主题域（DL2）应符合附录A的规定。  

# 6.1.2 识别研发业务对象  

# 6.1.2.1 业务对象识别原则  

整理主题域内的全部业务流程输入输出文件，应基于以下原则，识别、抽象归纳为候选业务对象：  

a) 重要性：是企业运作和管理中不可缺少的重要的人、事、物等信息;  
b） 唯一性：具有唯一身份标识信息;  
c) 独立性：相对独立并有属性描述，且不依赖其他业务对象实例消亡;  
d） 生命周期与状态：具有生命周期，存在状态变化，且状态变化不影响其身份唯一性;  
e） 可实例化：能够形成具体实例，具备实际落地的表现形式。  

# 6.1.2.2业务对象确定原则  

应按以下原则，整理、整合候选业务对象，确定业务对象：  

a）唯一性：业务对象仅在一个主题域定义，不应在各主题域重复创建;  
b） 多态整合：同一业务对象的不同场景、不同状态应合并为一个业务对象;  
c) 载体剥离：识别业务对象时，忽略业务对象的具体载体形式;  
d) 同质抽象：承载相同业务含义或用途的载体，应抽象整合为统一的业务对象。  

# 6.1.2.3业务对象命名原则  

业务对象命名应符合以下规定：  

a）准确性：应准确描述业务对象的功能、属性或特征，避免使用模棱两可或不具体的名称；  
b）简洁性：使用简洁明了的词语组合，避免冗长或复杂的表达方式;  
c）规范性：遵循通用的中文词汇和语法规范，使命名具有通用性和可理解性;  
d）一致性：在整个系统中保持一致的命名规则，使不同的业务对象具有相似的命名方式，便于理解和使用；  
e）可读性：使用易于理解和阅读的汉字或词语，避免使用生僻或不常见的词汇，以方便用户理解和使用；  
f）避免歧义：避免使用具有多种解释或歧义的词汇，以防止产生混淆或误解；  
g）避免与系统关键词冲突：避免使用与系统关键词相同或相似的词汇，以免产生命名冲突或混淆。

# 6.1.3定义逻辑数据实体和属性  

# 6.1.3.1定义逻辑数据实体  

应结合应用场景，基于以下原则识别并归纳属性集合，定义逻辑数据实体及其标识符（主键）：  

a）特征属性集合：选择描述某个或某些业务特征的多个属性，组成逻辑数据实体;  
b）逻辑关联性：逻辑数据实体应依托业务对象存在，业务对象与逻辑数据实体可以一对一或一对多，不应多对一;  
c）基础独立性：能够组合起来提供数据服务、满足下游的数据消费需求的若干属性，或跨业务领域使用的基础数据，可以设计成一个逻辑数据实体;  
d）属性原子性：逻辑数据实体的每一个属性数据都具有原子性;  
e）主键唯一性：每个逻辑数据实体应选取一个能与其他逻辑数据实体进行区分的属性或属性组，作为该实体的唯一标识;  
e）主键依赖性：每个逻辑数据实体中的非主键数据应完全依赖于主键，非主键数据之间不应有传递依赖关系。  

# 6.1.3.2 定义属性  

基于业务对象对应的业务流程输出文件和管理需求定义属性，应遵循以下原则以确保数据的有效性和可用性：  

a）业务导向：根据业务需求设计属性，确保能够准确反映业务对象的性质和特征;b）描述性：应对业务对象进行详细描述，作为数据分析和业务决策的重要依据;c） 唯一性：在同一业务对象中，每个属性应有唯一的名称，以区分不同的信息项;d） 准确性：属性的名称应能够清晰准确地表达其含义和用途，便于理解其代表的数据内容;e）原子性：每个属性都是最小数据单元，不可再分割，不能是集合、数组、记录等非原子数据项，即每个属性都只包含单一值;f）简洁性：避免设计冗余或不必要的属性，以减轻数据库负担并提高查询效率。以业务对象“产品物料”、“产品采购技术要求”、“产品图样”为示例，设计逻辑数据实体及属性，见附录C。  

# 6.2制定研发数据标准  

# 6.2.1 基本要求  

应从基础属性、业务属性、技术属性、管理属性四个维度制定属性的数据标准，形成企业层面需共同  

Q/CRRCJ278.3—2025  

遵守的定义和规则，满足业务管理、信息系统、数据分析应用需求。  

# 6.2.2 基础属性  

基础属性对属性的基本信息进行定义，如所属主题域、业务对象、中文名称等，应至少包括以下内容：  

a) 数据标准编号：明确属性的数据标准编号；  
b) 主题域分组：明确其所属的主题域分组;  
c) 主题域：明确其所属的主题域;  
d) 业务对象：明确其所属的业务对象;  
e) 逻辑数据实体：明确其所属的逻辑数据实体；  
f) 属性中文名称：明确属性的中文名称;  
g) 属性英文名称：明确属性的英文名称。  

# 6.2.3 业务属性  

业务属性从业务视角对属性进行统一和定义，对业务应用进行规范和约束，应至少包括以下内容：  

a）定义及用途：明确属性的业务定义及用途;  
b）业务规则：对属性相关业务的规则和约束进行定义，主要包括业务相关的管理章程、规章制度、行业标准、操作规范等;  
c） 允许值：根据业务规则确定数据是否有可供选择的允许值。如果属性有允许值，应列出允许值；  
d） 数据示例：描述业务属性的数据实例;  
e） 密级：明确属性的密级标准，如：普通商业秘密（简称普密）、核心商业秘密（简称核密）；  
f）是否制定标准：填写“是”或“否”，明确属性是否制定了标准;  
g） 引用标准：如果属性制定了标准，填写标准名称;  
h) 是否引用其它业务对象：填写“是”或“否”，明确属性是否直接引用其它业务对象;  
i) 引用的业务对象：明确具体引用的业务对象名称;  
j）引用的业务对象属性：明确具体引用业务对象下的属性名称。  

# 6.2.4 技术属性  

技术属性从信息技术视角对属性进行定义，对应用系统实施形成必要的指引和约束，应至少包括以下内容：  

a) 必填项：根据业务规则明确属性数据是否必填;  
b) 数据类型：明确属性数据的类型，一般为数字型、字符型、日期型、逻辑型、非结构型;  
c） 数据长度：明确属性数据的长度;  
d） 数据源：明确属性被初次创建时的应用系统。  

# 6.2.5 管理属性  

管理属性从业务和数据管理视角明确各部门应承担的责任，应至少包括以下内容：  

a） 业务规则责任主体：明确业务规则的制定部门，一般与数据责任人保持一致;  
b） 数据维护责任主体：明确数据创建、修改、删除的责任部门;  
c） 数据监控责任主体：明确数据监控的责任主体，一般与业务规则责任主体保持一致。  

以业务对象“产品物料”的属性“物料编码”为示例，其数据标准见附录D。  

# 6.3研发数据模型设计  

# 6.3.1 基本要求  

应根据已识别的业务对象、逻辑数据实体及属性，分别建立研发概念数据模型、逻辑数据模型和物理数据模型，可视化展现数据的组织及运行关系，指导应用系统开发。  

# 6.3.2 概念数据模型  

应从宏观角度分析和设计业务对象之间的关系，按照“E-R”实体-关系模型标准，建立概念数据模型：  

a）圈定业务范围，整理业务范围内的业务对象;  
b）布局业务对象，建立研发域的业务对象之间的关联关系（一对一、一对多、多对一或多对多等），构建模型图;  
c）梳理关联的外部业务对象，将相关的外部业务对象放置在外围，建立其与内部业务对象的联接。  
研发管理概念数据模型示例见附录E。  

# 6.3.3 逻辑数据模型  

应按照以下原则建立逻辑数据模型：  

a）整理业务对象的逻辑数据实体;  
b）绘制逻辑数据实体框图，从上至下分为三部分：逻辑数据实体名称（含属性数量）、逻辑数据实体主键（Primary Key,PK）、属性列表及外键（Foreign Key，FK）；  
c）主键（PK）是表中唯一标识每一行记录的字段或字段组合，一个表只有一个主关键字，主键的值必须是唯一的，不能有重复，不能为空，主键的值一旦确定，通常不应更改。主键确保表中每一行数据的唯一性，作为其他表引用该表数据的外键;  
d）外键（FK）是表中引用另一个表主键的字段或字段组合，外键的值应存在于被引用表的主键中，外键用于建立和强制表与表之间的关系；  
e）按照各逻辑数据实体之间的关系（一对一、一对多、多对一或多对多等），联接各逻辑数据实体框图。  
以“产品物料”为示例，逻辑数据模型见附录F。  

# 6.3.4物理数据模型  

信息技术人员应按照以下原则建立物理数据模型：  

a）以逻辑数据模型为基础，综合考虑数据库管理的特性、性能和存储要求，进行数据库整体设计；  
b）将逻辑数据模型中定义的逻辑数据实体、属性、属性约束、关系等内容，转换为数据库软件能识别的体现物理数据实体关系的数据库表或数据文件;  
c）定义用数据库模式来实现逻辑数据模型、保存数据的方式。  

# 6.4研发数据分布设计  

# 6.4.1 基本要求  

Q/CRRCJ 278.3—2025  

根据研发数据模型梳理确定研发信息链、数据流，明确各业务对象所属数据在各业务流程、各应用系统的分布关系和流转方向，明确数据源。  

数据分布设计应遵循最小化冗余原则：同一业务对象的相同属性在流转过程中仅允许在一个数据源存储，其他系统通过引用获取。  

# 6.4.2 研发信息链  

应按照以下原则设计信息链：  

a) 圈定业务范围，确定起始点和结束点；  
b) 梳理主要业务活动，绘制业务主要流程;  
c) 梳理业务范围内的业务对象，建立业务对象列表;  
d) 在业务活动附近适当位置标识业务对象的创建、读取、更新、删除信息。  
研发管理信息链示例见附录G。  

# 6.4.3 研发数据流  

应结合系统应用架构，按照以下原则设计数据流：  

a) 圈定业务范围，确定起始点和结束点；  
b） 梳理研发业务应用的信息系统平台，绘制应用系统平台框图；  
c） 梳理业务范围内的业务对象，建立业务对象列表；  
d）在信息系统平台框图附近适当位置标识业务对象的创建、读取、更新、删除信息。  
研发数据流示例见附录H。  

# 6.4.4研发数据源  

应按照以下原则明确数据源：  

a) 认证各项数据的数据源，并在企业范围内统一发布;  
b) 仅在数据源录入、修改数据，其它调用系统不能修改；  
c） 所有应用系统从数据源或数据源镜像获取数据。  
研发数据源示例见附录I。

# 编制说明  

# 1 工作简况  

# 1.1 编制依据  

根据“关于印发《中国中车2025年技术标准项目计划》的通知”（中车集团办科信（2025）95号）“2025CRRC010基于数智转型的研发数字化体系 第3部分：数据架构设计规范”的要求，由中车科技质量与信息化部归口，并由中车长春轨道客车股份有限公司、中国中车股份有限公司、中车株洲电力机车研究所有限公司、中车南京浦镇车辆有限公司、中车株洲电力机车有限公司、中车齐齐哈尔车辆有限公司、中车戚墅堰机车有限公司共同起草。  

本文件为首次制定。  

# 1.2制修订本标准的必要性  

为深入贯彻中车数智化转型整体战略，培育和发展数智转型的新质生产力，以研发数字化为核心支撑轨道交通装备和清洁能源装备技术创新以立新优势，系统性推进研发数智化工作。在归口单位建立的《研发数字化体系建设专项方案》指导下，通过对国内外研发数字化体系现状充分研究，形成《研发数字化体系》系列标准制定工作任务，本文件为系列标准第3部分《研发数字化体系数据架构设计规范》，系统性指导研发数据架构设计工作。  

# 1.3 编制过程  

在本文件的编制过程中，完成了大量的基础研究和编写工作，并邀请了国内和铁路行业相关领域的专家进行了技术审查，确保了标准的规范性和权威性。本文件编制过程概要如下：  

（1）标准计划下达后，在归口单位指导下，中车长春轨道客车股份有限公司、中国中车股份有限公司、中车株洲电力机车研究所有限公司、中车南京浦镇车辆有限公司、中车株洲电力机车有限公司、中车齐齐哈尔车辆有限公司、中车戚墅堰机车有限公司等单位成立了标准起草组，对研发数据架构核心构成要素等情况进行了调研，收集了相关技术资料，初步形成了工作大纲和本文件的草案稿。  

（2）通过专项研讨方式，归口单位组织多轮次的草案稿研讨，研讨参与单位除起草组外包含中车大连机车车辆有限公司、中车唐山机车车辆有限公司、中车大同电力机车有限公司、中车信息技术有限公司、中车重庆智慧轨道交通技术有限公司、中车启航新能源技术有限公司等。  

（3）标准起草组对前期工作和标准草案深入讨论研究后，2025年6月形成了本文件的征求意见稿并发送株洲所，由株洲所审查后上报中车科技质量与信息化部，征求意见稿发往中车各一级子公司进行意见征集。

# 2 编制原则  

2.1标准格式统一、规范，符合GB/T1.1—2020要求。  

2.2标准内容符合统一性、协调性、适用性、一致性、规范性要求。  

2.3标准内容具有系统性、科学性、指导性。  

2.4 标准实施后有利于系统性指导集团、子企业的研发数字化建设工作，符合集团研发管理总体发展需求。  

# 3 主要内容  

3.1本标准规定了中车各企业进行研发数据架构建设时的总则和步骤，搭建数据资源目录、制定数据标准、绘制数据模型、规划数据分布、统一业务定义和数据标准，适用于中车各企业开展研发数据架构建设。  

3.2本标准依据GB/T34960.5—2018《信息技术服务治理第5部分:数据治理规范》、GB/T36073—2018《数据管理能力成熟度评估模型》、GB/T40685—2021《信息技术服务数据资产管理要求》、Q/CRRCJ278.2—2025《研发数字化体系第2部分：流程管理规范》等技术规范，结合实际应用编制。  

3.3经起草组分析研究，与本标准/本部分主要技术内容有关联的现行国家标准、行业标准的关联关系及后续工作建议见表1。

# 4 关键指标的确定  

4.1研发数据架构设计：搭建数据资源目录、制定数据标准、绘制数据模型、规划数据分布、统一业务定义和数据标准，使系统功能更好支撑业务场景，消除信息孤岛，实现业务和系统端到端贯通，在集团公司层面统一研发数据架构建设的基本框架。  

4.2数据分层设计：数据资源目录构建统一遵照“DL1主题域分组、DL2主题域、DL3业务对象、DL4逻辑数据实体、DL5属性”五层数据分层架构。  

4.3数据标准覆盖性：研发数据标准应覆盖基础、业务、技术、管理四个维度，以满足未来研发业务管理、信息系统、数据分析应用需要。
